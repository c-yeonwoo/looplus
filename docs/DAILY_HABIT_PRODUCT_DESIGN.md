# Looplus: 일상 실천 앱으로의 전환 설계

> 작성: 2026-10-23 · 기준 코드: `2d8ac91` · 상태: **제품·기능 설계 제안 / 구현 전**
>
> 확인된 방향: 개인 습관·동기부여 중심, iOS·Android 출시, 순차 출시 가능.
> 2026-10-23 추가 승인: **오늘·목표·기록 3탭, 금융의 선택형 전환, 네 가지 핵심 흐름 화면 설계 진행**.
> 이 문서는 금융 중심의 기존 `ROADMAP.md`를 대체할 설계안이다. 세부 기능·스택·일정 전체가 승인되거나 구현된 것은 아니다.
> 기능 동작·데이터 정책·실험을 먼저 설계한다. 픽셀 수준 화면, 시각 리브랜딩, 프레임워크 최종 선택은 아직 승인되지 않았다.

## 1. 핵심 결론

현재 Looplus는 **자산 계획에 루틴을 연결한 제품**이다.
새 제품은 **일상 실천에 목표와 회고를 연결한 제품**이어야 한다.
둘은 홈 화면의 우선순위, 첫 입력, 성공 지표, 저장 모델까지 다르다. 메뉴명 교체만으로 전환되지 않는다.

제안하는 제품 약속:

> **작게 시작하고, 나에게 맞게 이어가요.**
> 오늘 가능한 실천을 정하고, 쌓인 변화를 확인하고, 쉬었다면 다시 이어가는 앱.

핵심은 ‘의욕을 계속 높이는 앱’이 아니라 **의욕이 낮은 날에도 선택 가능한 행동이 남는 앱**이다.
Loop는 실행→기록→조정→재실행, Plus는 그 과정에서 쌓이는 실제 경험과 변화로 해석한다.
이 의미를 설명문으로만 전달하지 않고, 오늘의 실천과 다음 주 계획이 실제로 연결되는 동작으로 증명한다.

‘완벽한 제품’은 모든 기능을 갖춘 제품이 아니라 다음 네 가지를 안정적으로 하는 제품으로 정의한다.

1. 첫 사용자가 설명 없이 한 가지 실천을 시작한다.
2. 바쁜 사용자가 짧게 기록하고 바로 일상으로 돌아간다.
3. 며칠 쉬어도 과거의 노력이 사라지거나 복귀가 부담스럽지 않다.
4. 앱을 껐다 켜거나 기기를 바꿔도 기록이 믿을 만하다.

## 2. 진단 방법과 한계

### 실제 확인한 것

- 코드: 홈·온보딩·탐색·루틴·목표 상세·주간 점검·날짜 계산·저장·동기화·분석 이벤트.
- 격리된 로컬 브라우저: 로그인 → 게스트 → 온보딩 건너뛰기 → 홈 → 루틴.
- 모바일 웹 390×844, 데스크톱 웹 1440×900. 실제 사용자 계정이나 기존 브라우저 데이터를 수정하지 않았다.
- 테스트: `npm test`, **12개 테스트 파일 / 87개 테스트 통과**.
- 앱 정책·경쟁 제품·행동 연구는 공식 자료를 확인했다. 외부 자료는 해당 절에 링크한다.

### 아직 확인하지 않은 것

운영 사용자 수·D7/D28 유지율·인터뷰·결제 의향·알림 수신 성공률·실제 서버의 RLS 상태·네이티브 성능은 미검증이다.
브라우저 에뮬레이션을 iOS/Android 실기기 검증으로 취급하지 않는다.
아래의 ‘사용자가 부담을 느낀다’ 같은 해석은 관찰된 구조에 대한 **제품 가설**이며 인터뷰 결과가 아니다.
단위 테스트 통과가 제품 방향, 저장 안전성 전체, 앱 출시 적합성을 보증하지 않는다.

## 3. As-is: 무엇이 강점이고 무엇이 막히는가

### 유지할 자산

- 목표 ↔ 루틴 ↔ 주간 점검의 연결 구조: 단순 체크리스트를 넘어설 기반.
- 계정 없는 시작, 로컬 저장, 저장 상태 표시: 첫 사용과 신뢰의 출발점.
- 목표 수치 도달과 사용자의 완료 기록 분리: 숫자만으로 성취를 강제하지 않는 원칙.
- 금융 엔진·지출 모델·테스트: 폐기할 대상이 아니라 선택형 전문 도구 후보.
- 일관된 기존 디자인 토큰: 새 방향을 검증하기 전 전면 스타일 교체를 할 이유는 없다.

## 4. 누구에게 먼저 유용해야 하는가

‘누구나’는 첫 타깃을 모두로 잡는다는 뜻이 아니라 **처음 배워야 할 개념과 필수 입력을 줄인다**는 뜻이다.

첫 타깃은 확정된 개인 사용자 중 다음 상황을 우선 검증한다.

- 시작은 자주 하지만 바쁜 주가 오면 멈추는 사람.
- 하루 1–3개 실천부터 이어가고 싶은 사람. 1–3개는 추천 시작량이지 강제 개수 제한이 아니다.
- 상세 프로젝트 관리보다 ‘오늘 뭘 하면 되는가’를 알고 싶은 사람.

대표 사용 장면(설계용 가상 사례):

| 장면 | 사용자가 원하는 것 | Looplus의 도움 |
|---|---|---|
| 퇴근 후 책 읽기 | 피곤해도 아주 조금은 이어가기 | 기본 10분, 바쁜 날 2분, 잠자리 준비 후라는 계기 |
| 일주일에 세 번 산책 | 일정이 바뀌어도 이번 주 안에서 실천 | 특정 요일 강제 없이 주 3일, 오늘 선택 가능 |
| 지출 살펴보기 | 돈 관리를 복잡한 투자 계획 없이 시작 | 주 1회 지출 확인 루틴, 원할 때 금융 도구 연결 |

첫 출시 비대상: 조직 OKR, 업무 협업, 공개 피드, 전문 운동 처방, 치료·진단, 투자 자문.
이후 소그룹 확장은 개인 가치가 검증된 뒤 선택한다. 이전 ‘원팀·원비전’은 우선 **기능들이 같은 개인의 목표를 위해 일한다**는 제품 통합 원칙으로 이어간다.

## 5. 시장 안에서의 위치와 근거

- **Streaks**는 간단한 체크, 반복 주기, 위젯·타이머·기기 연결을 제공한다. 설치 앱의 빠른 실행 수준을 참고한다. [공식 제품 소개](https://streaks.app/)
- **Habitify**는 일정·추세·타이머·여러 연동을 소개한다. 풍부한 추적 자체만으로는 차별화가 어렵다. [공식 제품 소개](https://habitify.me/)
- **Finch**는 작은 자기돌봄 행동과 가상 친구를 연결하고, 목표의 중지·미루기 기능도 안내한다. ‘따뜻함’이나 ‘쉬기’만으로 독점적인 차별성을 주장할 수 없다. [공식 소개](https://finchcare.com/about-finch), [목표 관리 안내](https://help.finchcare.com/hc/en-us/articles/37779940291213-Creating-and-Completing-Goals)

이 비교는 공식 공개 자료의 기능/포지셔닝 비교다. 경쟁 앱 전체 실사용 평가나 시장점유율 분석은 아니다.

Looplus의 검증할 차별화 가설은 다음 **조합의 마찰이 낮다는 것**이다.

> 목표와 연결된 오늘의 행동 → 작게 하는 대안 → 실제 기록 → 한 가지 계획 수정 → 다음 주에 자동 반영.

Lally 등의 연구는 습관 자동화에 개인차가 크고 한 번의 수행 기회를 놓치는 것이 과정에 실질적 영향을 주지 않았다고 보고했다.
따라서 ‘21일이면 완성’, ‘하루 놓치면 처음부터’를 제품의 사실처럼 말하지 않는다.
이 연구가 Looplus의 복귀 기능 효과를 입증하는 것은 아니다. 복귀 설계는 별도 제품 실험으로 검증한다. [원 논문](https://onlinelibrary.wiley.com/doi/10.1002/ejsp.674)

## 6. 제품 구조: 깊이는 내부에, 단순함은 사용자에게

사용자 언어는 **목표 · 루틴 · 기록**으로 단순화한다.
‘비전·마일스톤·액션·루프’를 첫 진입 때 모두 만들게 하지 않는다.

- **목표:** 이루고 싶은 변화. 예: 올해 책 12권 읽기. 없어도 시작 가능.
- **중간 목표:** 큰 목표를 나눌 때만 펼치는 선택 기능. 기존 마일스톤 개념은 여기로 정리하는 것을 제안.
- **루틴:** 반복할 행동. 예: 잠자리 준비 후 10분 읽기. 목표 연결은 선택.
- **기록:** 실제 한 일과 돌아본 내용. 목표 수치와 실행 빈도는 다른 증거로 보관.
- **오늘 한 번 할 일:** 회고에서 나온 비반복 행동. 반복 루틴으로 강제 변환하지 않음. v1.1 후보.

승인된 정보 구조(화면 세부안은 별도 검토):

| 목적지 | 사용자의 질문 | 주요 내용 | 다음 화면으로 전달되는 것 |
|---|---|---|---|
| **오늘** | 지금 무엇을 하면 되지? | 예정 루틴, 주간 자유 실천, 추가, 작게 하기 | 선택한 루틴의 실행 기록 |
| **목표** | 왜 하고 있고 어디까지 왔지? | 선택한 목표, 중간 목표, 연결 루틴, 실제 성과 | 목표 맥락을 가진 루틴 추가/실행 |
| **기록** | 무엇이 쌓였고 무엇을 바꿀까? | 달력, 루틴별 이력, 주간 돌아보기 | 유효일이 있는 다음 계획 |

설정·계정·알림·데이터 관리는 프로필 진입점에 둔다. 루틴 전체 관리는 오늘 화면에서 접근한다.
금융은 선택형 ‘돈 관리 도구’로 분리한다. 세부 진입점은 `CORE_FLOWS_SCREEN_DESIGN.md`에서 제안한다.
기존 `/engine`, `/spending`, `/tracking`, `/goals/:id` 링크는 호환 경로를 유지한다.

모든 화면·위젯·알림은 같은 `goalId/habitId/occurrenceId`와 공통 계산 규칙을 사용한다.
URL 이동만 연결된 상태는 충분하지 않다. 한 번 수정한 다음 주 계획이 오늘 목록과 알림에도 반영되어야 한다.

## 7. 대표 경험: 처음 1분부터 다음 달까지

### A. 첫 사용 — 가입·목표·금융 정보 없이

1. 첫 화면의 주 행동: ‘루틴 하나 시작하기’. 계정 복원은 보조 행동.
2. 대표 루틴에서 선택하거나 직접 만든다. 첫 화면은 편집 선정 6개, 전체 목록은 6개 분류·24개로 제안한다. 카테고리 선택·성격 설문을 필수로 요구하지 않는다. 상세는 화면 설계 v0.2의 F1-01을 따른다.
3. 무엇을 할지, 어느 주기로 할지 정한다. ‘작게 할 때’와 ‘언제 떠올릴지’는 선택 필드.
4. 오늘 목록에 실제 루틴을 만든다. 기본 일정도 저장 전에 보여주며 자동으로 완료하지 않는다.
5. 지금 했다면 기록한다. 아직 안 했다면 나중에 기록하도록 둔다.
6. 알림을 켜기로 선택한 순간에 권한 요청. 백업 계정은 가치 경험 이후 제안.

목표: 첫 루틴 생성 60초 이내는 **사용성 목표**다. 실제 행동이 10분 걸리는 루틴까지 60초 내 완료시키겠다는 뜻이 아니다.
게스트에게 ‘이 기기에 저장, 앱 삭제 시 사라질 수 있음’을 짧게 알리고 내보내기/백업 경로를 둔다.

### B. 매일 — 한 번 열고 할 일을 알 수 있게

오늘 화면의 우선순위는 날짜/동기화 상태 → 오늘 실천 → 이번 주 자유 실천 → 완료 항목이다.
목표 맥락은 해당 루틴의 짧은 보조 문구로 보여준다. 큰 자산 그래프·전체 성적표·홍보 배너는 앞에 두지 않는다.
‘오늘 집중할 하나’는 사용자가 고를 수 있지만 필수 단계나 다른 루틴을 막는 제한으로 만들지 않는다.

- 체크형: 명확한 탭 영역에서 완료, 바로 되돌리기.
- 수량형: 예를 들어 페이지 수 직접 기록, 최근 입력량을 빠르게 재사용.
- 시간형: 실제 분량 직접 기록. 타이머는 편의 기능이지 기록의 필수 전제는 아니다.
- 카드 본문은 상세, 체크 영역은 완료처럼 역할을 분리한다. 스와이프는 보조 경로이며 유일한 경로가 아니다.
- 완료 후에는 실제 수치만 짧게 피드백: ‘이번 주 두 번째 실천이에요.’ 과장된 인생 점수는 만들지 않는다.
- 완료 항목 이동으로 누르려던 다음 항목이 바뀌지 않도록 즉시 재정렬을 피한다.

### C. 의욕이 낮은 날 — ‘작게 하기’

독서 10분 대신 2분처럼 사용자가 미리 정한 최소 행동을 제공한다.
일반 목표를 몰래 낮추거나 최소 실천을 원래 목표 완료로 위장하지 않는다.
기록에 실제 수량/시간과 ‘작게 실천’을 남기고, 원하면 같은 날 더 이어서 정규 목표를 채운다.
최소 행동을 안 정했다면 강요하지 않고 일반 기록·쉬기만 제공한다.

### D. 쉬고 돌아온 날 — 밀린 숙제를 만들지 않기

미기록 기간은 그대로 남기고 오늘 날짜로 돌아온다. 누적 미완료를 자동으로 오늘로 이월하지 않는다.
다음 예정 기회를 두 번 연속 놓쳤을 때 복귀 제안을 보여주는 것은 초기 가설이며, 주 N일 루틴은 일별 공백으로 판단하지 않는다.

제안은 세 가지: ‘오늘은 작게’, ‘횟수 줄이기’, ‘더 쉬기’. dismiss 가능하고 자동 변경하지 않는다.
‘3일이나 놓쳤어요’ 대신 ‘오늘 가능한 크기로 다시 시작해요’를 사용한다.
과거 실천을 나중에 기록할 수 있으나 ‘오늘 활동’이나 알림 반응으로 중복 집계하지 않는다.

### E. 주간 돌아보기 — 보고서가 아니라 다음 주를 바꾸는 작업

약 60–90초를 목표로 네 단계만 제공한다.

1. **사실:** 정규 실천·작게 실천·쉼을 구분한 일주일. 수치 변화는 별도.
2. **느낌:** 괜찮았어요 / 조금 버거웠어요 / 바꿔보고 싶어요. 선택 입력.
3. **한 가지 결정:** 유지 / 크기·횟수 조정 / 기간 정해 쉬기.
4. **적용 미리보기:** ‘다음 월요일부터 읽기 10분 → 5분, 주 5일 → 3일’. 확인하면 일정/알림 함께 변경.

전체 회고와 목표별 결정은 별도로 저장한다. 목표 A에서 작성한 메모를 B에 표시하지 않는다.
기본 적용일은 다음 주 시작, 오늘부터 바꾸려면 명시적으로 선택한다. 중간 저장·다시 열기·취소를 지원한다.

### F. 목표 달성 — 일상은 끝나지 않는다

독서 루틴 20회가 책 12권 완독과 같지 않다. 실행량과 결과량을 나란히 보여준다.
같은 단위의 직접 기여일 때만 명시적으로 자동 합산하고, 목표 기간의 기록만 포함한다.
달성 시 ‘완료 기록 → 유지 루틴으로 이어가기 / 다음 목표 / 잠시 쉬기’를 선택한다.
끝없는 새 목표 생성을 강요하지 않는다. 유지도 유효한 성공이다.

## 8. 기능 범위: 최소 기능이 아니라 최소 완결 경험

| 구분 | 기능 | 이유/경계 |
|---|---|---|
| v1 필수 | 금융 없는 게스트 온보딩·오늘 화면 | 새 정체성의 입구 |
| v1 필수 | 독립 루틴, 체크·수량·시간 직접 기록 | 일상 행동을 왜곡 없이 표현 |
| v1 필수 | 매일·고정 요일·주 N일 | 불규칙 일상 대응. v1 주 N일은 하루 최대 한 번 충족 |
| v1 필수 | 최소 행동, 당일 쉬기, 기간 일시정지, 재개 | 복귀 경험의 실체 |
| v1 필수 | 간단한 목표 연결, 실제 성과 수동 입력 | 기존 강점 유지. 다단계 의존 그래프는 제외 |
| v1 필수 | 기록 달력, 루틴 이력, 짧은 주간 돌아보기 | 실행에서 다음 계획으로 연결 |
| v1 필수 | 사용자 지정 로컬 알림, 거부/취소 경로 | 앱을 열지 않은 날에도 필요한 맥락 제공 |
| v1 필수 | 오프라인 저장, 재시도, 안전한 계정 병합 | 기록 신뢰성 |
| v1 필수 | 보관/삭제 구분, 내보내기, 계정 삭제 | 기록 소유권과 스토어 준비 |
| v1.1 | 홈 위젯의 오늘 목록·직접 기록 | 높은 일상 효용, OS별 별도 품질 게이트 |
| v1.1 | 내장 타이머, 하루 한 번 할 일 | 수동 기록·다음 계획 이후의 편의 강화 |
| v1.1 | 목표의 중간 단계·월간 변화 요약 | 기록이 쌓인 뒤 의미 있는 확장 |
| 이후 검증 | 소그룹 응원, 캘린더/건강 연동, AI 제안 | 권한·운영·민감정보·비용 증가를 정당화할 증거 필요 |

첫 출시에서 제외: 경쟁 순위, 연속 기록 복구 결제, 포인트 상점, 범용 AI 대화 탭, 공개 소셜 피드, 금융 제휴 CTA, 자동 건강 진단.
물 마시기·수면·복약처럼 개인별 맥락이 다른 행동에 획일적 수치나 의료적 효과를 기본값으로 강요하지 않는다.
위젯은 기술 검증을 일찍 하되 출시 필수와 분리한다. 위젯 하나 때문에 핵심 기록 안전성을 희생하지 않는다.

## 9. 실행 상태와 집계 규칙

상태 수를 화면에 전부 노출하지 않되 모델에서는 구분한다.

| 상태 | 의미 | 오늘/기록 표시 | 정규 달성률 처리 |
|---|---|---|---|
| 예정 | 해당 기간에 하기로 함 | 오늘 할 일 | 기간이 끝나기 전 실패 아님 |
| 일부 기록 | 실제 수량 > 0, 목표 미달 | ‘4/10분’ | 정규 완료 아님 |
| 작게 실천 | 미리 정한 최소 행동 충족 | ‘작게 2분’ | 별도 실천 수, 정규 완료와 구분 |
| 완료 | 해당 계획 버전의 정규 기준 충족 | 체크 + 실제 값 | 분자에 포함 |
| 오늘 쉬기 | 사용자가 해당 기회만 쉬기로 선택 | ‘쉼’ | 예정 분모에는 남기되 실패 경고 없음 |
| 미기록 | 마감까지 기록/쉼 선택이 없음 | 중립적 빈 기록 | 예정 분모에 남음 |
| 일시정지 | 기간 동안 향후 계획을 중단 | 재개일/직접 재개 | 유효 기간의 예정 생성 안 함 |
| 보관 | 더 이상 반복하지 않음 | 이력에서 접근 | 보관 이후 예정 생성 안 함 |

화면의 기본 요약은 ‘정규 3회 · 작게 1회 · 쉼 1회’다. 서로 다른 의미를 100% 한 숫자로 숨기지 않는다.
정규 달성률은 마감된 예정 기회 대비 정규 완료이며, 작게 실천을 포함한 참여 지표는 별도 이름과 설명을 둔다.
일시정지·일정 수정은 원칙적으로 앞으로만 적용한다. 과거 계획을 바꿔 성적을 올리는 경로를 만들지 않는다.
기록 수정은 허용하되 수정 이력과 당시 계획은 보존한다. 상세 이력 정정은 회고 재계산 여부를 사용자에게 알린다.

주 N일은 **해당 주에 조건을 충족한 서로 다른 날짜 N개**다. 하루 다섯 번 체크해도 5일이 되지 않는다.
주 N일을 7개의 일별 미완료로 만들지 않고, 진행 중에는 ‘이번 주 1/3일’로 표현한다.
최소 행동 충족 일수와 정규 충족 일수는 분리한다. 한 날짜는 최종 상태 기준 한 번만 집계한다.
v1에서는 빈도 단위 ‘주 N회(같은 날 여러 번)’를 지원하지 않아 날짜형과 횟수형 의미가 섞이지 않게 한다.
루틴 생성 전 날짜·미래 날짜·일시정지 기간을 실패로 만들지 않는다.

## 10. 핵심 데이터 모델 제안

기존 `GoalLoop`와 `Tracking` 이름을 UI에서 바로 전면 교체하는 것보다, 도메인을 분리하고 호환 어댑터를 둔다.

| 객체 | 책임/주요 속성 | 중요한 불변 조건 |
|---|---|---|
| Goal | 제목, 이유, 측정 단위, 기간, 상태 | 실행 빈도와 결과 진척 분리 |
| GoalMeasurement | 실제 결과값, 측정일, 출처 | 예측값과 실제값 구분 |
| Habit | 제목, 목표 연결(선택), 계기, 기록 방식, 상태 | 목표 없이도 존재 가능 |
| HabitPlanVersion | 유효 시작일, 주기, 정규/최소 기준, 시간대 | 과거 계획 덮어쓰기 금지 |
| PauseInterval | 시작일, 종료일 또는 직접 재개 | 알림과 예정 계산이 같은 기간을 사용 |
| Occurrence | habitId, 기간/날짜 키, 당시 planVersion 참조 | 동일 기회가 화면/기기별로 중복 생성되지 않음 |
| HabitEntry | entryId, 실제 값, 발생시각, 귀속일, 시간대, 출처 | 재전송은 새 실천이 아님 |
| EntryRevision | 수정/취소, 이전 revision, 변경 시각 | 완료 취소도 안전하게 동기화 |
| WeeklyReview | 기간, snapshot, 전체 메모, 초안/확정 | 저장된 당시 요약과 최신 재계산 구분 |
| PlanAdjustment | 대상 id, 변경 내용, 적용일, 확인 상태 | 회고 저장과 적용이 반쯤 성공하지 않음 |
| Reminder | 기기, 대상, 시각, 권한·예약 상태 | 중지/완료/삭제 시 해당 예약 정리 |
| OutboxOperation | opId, payload, baseRevision, 재시도 상태 | 도메인 저장과 같은 로컬 트랜잭션 |

### 날짜·시간대

- 최초 기기 시간대를 제안하고 프로필의 기준 시간대를 저장한다. 기본 일 경계는 00:00.
- UTC 발생시각과 사용자 귀속 날짜/시간대를 함께 저장한다. 날짜를 UTC 문자열 절단으로 만들지 않는다.
- 여행 중 시간대 변경은 사용자에게 제안하고 앞으로 적용한다. 과거 기록은 재귀속하지 않는다.
- DST·자정 직전 기록·오프라인 지연 업로드는 테스트 대상으로 고정한다.
- 동일 예정 기회의 키는 habit/기간/slot에 기반하며 계획 수정 때마다 새 기회로 중복 생성되지 않는다.
- 야간근무용 사용자 지정 하루 경계는 v1.1 후보. v1은 기준 시간대와 과거 날짜 기록으로 대응한다.

### 과잉 설계 방지

전체 서비스에 범용 이벤트 소싱·CRDT를 먼저 도입하지 않는다.
루틴/계획/실행 기록에 한정해 안정적 ID, revision, 기록 정정, outbox를 구현한다.
클라이언트에는 UI가 읽기 쉬운 projection을 제공하고, 금융 계산은 별도 모듈로 유지한다.

## 11. 오프라인·동기화·이전 설계

‘이 기기에 저장됨’과 ‘계정에 백업됨’을 같은 성공 문구로 표현하지 않는다.

1. 완료 탭 → 로컬 DB에 기록과 outbox를 **함께** 저장 → UI 완료 표시.
2. 저장 실패면 완료처럼 확정하지 않고 재시도 가능한 상태를 표시한다.
3. 연결되면 opId 기반 멱등 API로 전송 → 서버 확인 → outbox 정리.
4. 서버 커서 기반으로 다른 기기의 변경 수신. 앱 재시작/포그라운드/재연결에서 재시도.
5. 서로 다른 날짜 기록은 합친다. 같은 기록을 두 기기에서 수정하면 baseRevision 충돌을 감지하고 두 버전을 보존한다.
6. 충돌을 조용한 마지막 쓰기 덮어쓰기로 숨기지 않는다. 비충돌 항목은 계속 쓰며 해당 기록만 선택하게 한다.

기록 보관과 계정 영구 삭제는 다르다. 보관은 이력을 남기고, 영구 삭제는 확인·재인증·처리 범위 안내 후 연관 데이터까지 처리한다.
동기화용 tombstone/운영 로그·백업의 보존 기간도 정책으로 명시하고 무기한 개인 기록 보존의 핑계로 쓰지 않는다.
인증 토큰은 OS 보안 저장소, 데이터는 계정별 분리 저장한다. 로그아웃/계정 전환에서 다른 사람 기록이 섞이지 않게 한다.
동기화 설정이 없거나 실패한 상태를 백업 완료로 표시하지 않는다.

### 기존 사용자 이전

- 기존 프로필 원본을 변경하기 전 사용자 내보내기와 서버 백업/복원 절차를 확보한다.
- `daily/weekdays`는 최초 계획 버전으로 옮기되, 과거 일정 변경 이력은 복원할 수 없음을 명시한다.
- boolean 완료는 체크형 기록으로 옮긴다. 알 수 없는 완료 시각·과거 분모는 만들어내지 않는다.
- 기존 누적 완료 사실은 보존하고, 불확실한 과거 완료율은 ‘이전 기록’으로 구분한다.
- 금융 목표는 금융 지표 adapter로 연결한다. 수동 %는 숫자 결과 측정으로 거짓 변환하지 않는다.
- 주간 점검은 legacy 금융 snapshot으로 보존하고 새 일반 회고와 구분한다.
- 게스트→새 계정은 import, 게스트→기존 계정은 양쪽 개수/중복을 보여주고 병합 선택. 원격 전체로 무조건 교체하지 않는다.
- `migrationVersion`과 안정적 legacy id 매핑으로 재실행 시 중복을 막는다.
- 단계별 read 전환과 기능 플래그를 사용한다. 양쪽 모델을 무기한 이중 쓰기하지 않는다.
- 전환 후 새 기록을 구버전이 덮어쓰지 못하도록 서버에 최소 클라이언트/스키마 버전 정책을 둔다.
- 롤백은 화면·읽기 경로 복구가 기본이다. 새 기록을 구버전 boolean으로 손실 변환하는 롤백은 금지한다.

## 12. 앱 기술 전략

**우선 추천 가설: Expo/React Native로 핵심 모바일 경험을 만들고, 순수 TypeScript 도메인을 공유한다.**
기존 Next.js 금융 화면 전체를 네이티브로 재작성하지 않는다. 웹 자산은 유지한다.
현재 React 컴포넌트가 자동으로 React Native UI가 되는 것은 아니다. DOM/Tailwind/Next route/SVG 캔버스의 재사용 범위는 제한적이다.

| 선택지 | 장점 | 비용/위험 | 판단 |
|---|---|---|---|
| PWA 유지 | 현재 코드 검증이 빠름 | 목표한 두 앱스토어의 앱 출시 전략과 동일하지 않음 | 웹 검증/기존 도구 유지용 |
| Capacitor | 웹 UI 재사용과 네이티브 플러그인 접근 | 현재 Next 서버 의존, 번들/오프라인 부트, 키보드·탐색·위젯 별도 작업 | 시간·인력 제약이 크면 비교 후보 |
| Expo/React Native | React/TS 경험 활용, 네이티브 탐색·로컬 DB·알림 구성 | 핵심 UI 재구현, 위젯·플랫폼별 코드 검증 필요 | 일상 모바일 제품의 우선 후보 |
| Swift/Kotlin 별도 | 각 OS 제어가 큼 | 두 UI·개발 체계 운영 비용 | 현재 소규모 전환의 기본안은 아님 |

Expo의 알림 API와 앱 재시작 후 유지되는 SQLite 저장소, Capacitor의 네이티브 플러그인 접근은 공식 문서로 확인했다.
이 기능 존재만으로 동기화·알림 전달·위젯이 완성되거나 출시가 보장되는 것은 아니다. [Expo 알림](https://docs.expo.dev/versions/latest/sdk/notifications/), [SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/), [Capacitor](https://capacitorjs.com/docs)

스택 확정 전 3–5개 작업일 기술 실험:

- 양 OS에서 루틴 체크 → 앱 강제 종료 → 오프라인 재실행 → 값 유지.
- 로컬 알림 예약/취소, 권한 거부, 앱 종료 상태의 알림 진입.
- 동일 occurrence를 앱/알림에서 반복 실행해도 중복되지 않는지.
- VoiceOver/TalkBack·큰 글자·키보드·뒤로가기.
- 작은 위젯 PoC의 앱 데이터 접근/동기화/배포 제약. 미통과 시 v1.1로 유지.
- 기존 금융 웹 도구 연결과 계정 경계. WebView를 끼워 넣는 것만으로 통합 인증이 해결되었다고 보지 않는다.

이 실험 결과와 실제 인력으로 스택·공수 ADR을 확정한다. 이번 설계에서는 패키지 설치나 리포 구조 재편을 수행하지 않는다.

## 13. 알림은 동기부여가 아니라 사용자가 정한 약속의 보조

- 첫 실행 즉시 권한을 요청하지 않는다. 사용자가 ‘이 시간에 알려줘’를 선택한 맥락에서 요청한다.
- 기본은 off. 권한 거부해도 모든 핵심 기록 기능 사용 가능.
- 기본 제안은 하루 묶음 1회, 원하는 경우 루틴별 시각을 직접 추가. 조용한 시간 설정 제공.
- 정규 완료/최소 실천/당일 쉼 후에는 해당 기회의 독촉 알림을 중지한다. 최소 실천 후 추가 알림은 기본 off.
- 기간 일시정지/보관/계정 삭제 시 예약 취소. 서버와 기기 알림을 이중 발송하지 않는다.
- 기기별 알림 설정을 명시해 다른 기기에 로그인했다고 모두 울리지 않게 한다.
- ‘알림 예약됨’과 ‘실제 사용자에게 전달됨’을 구분한다. OS 절전·집중 모드·권한 때문에 정시 전달을 보장하지 않는다.
- 알림 본문은 기본적으로 민감한 목표명을 숨길 수 있게 한다. 제목·습관 내용은 분석 로그에 보내지 않는다.
- 자동 확대된 리마인더나 광고성 푸시는 v1에 없다. 미반응은 알림을 더 보내야 한다는 동의가 아니다.

Android 13 이상 알림 권한과 맥락 있는 요청의 필요성은 공식 문서에 따른다. [Android 알림 권한](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

## 14. 접근성·품질·시각 방향의 경계

현재의 잉크/틸 브랜드와 로고를 기준 자산으로 유지하되, 화면 구성은 일상 실행 우선으로 바꾼다.
새 팔레트·캐릭터·감성 이미지는 이번 설계에서 결정하지 않는다. 동기부여를 위해 마스코트가 반드시 필요한 것은 아니다.
새 화면 시안은 제품 구조 승인 후 동등한 구조 대안을 비교하고 선택한다.

- 핵심 탭은 세 개, 각 탭은 행동 버튼이 아니라 목적지.
- iOS 44pt·Android 48dp 이상의 터치 영역, 아이콘과 텍스트로 상태 전달.
- iOS 네이티브 뒤로가기/시트, Android 시스템 Back/예측 Back과 키보드 inset을 보존한다.
- 큰 글자·다크 모드·읽기 순서·VoiceOver/TalkBack·동작 줄이기 대응.
- 완료/저장 실패/충돌 상태를 색만으로 구분하지 않는다.
- 첫 빈 상태: 통계 대신 예시와 생성 CTA. 기록이 쌓인 뒤에만 추세를 보여준다.
- 루틴 0/1/3/20개, 긴 한국어·이모지 제목, 연결 목표 없음/보관됨, 네트워크 없음 상태를 설계한다.
- ‘오늘 할 일 없음’과 ‘이번 주 자유 실천이 남음’을 구분한다. 쉬는 날에 새 목표 만들기를 압박하지 않는다.
- 데이터가 적을 때 ‘패턴 분석 완료’ 같은 과장된 인사이트를 만들지 않는다.

## 15. 출시 요건: 앱 모양만으로는 부족하다

Apple은 재포장한 웹사이트를 넘어서는 유용성과 앱 경험을 요구하고, 계정 생성 기능이 있다면 앱 내 계정 삭제도 요구한다.
이는 특정 프레임워크 금지가 아니며, 네이티브 프레임워크를 쓴다고 심사가 보장되는 것도 아니다. [App Review Guidelines 4.2 / 5.1.1](https://developer.apple.com/app-store/review/guidelines/)

Google Play는 계정 생성 앱에 앱 내 삭제 요청 경로와 외부 웹 삭제 요청 경로를 요구한다.
게스트 기능이 있다고 계정 삭제 요건이 없어지지 않는다. [Google Play 계정 삭제 요건](https://support.google.com/googleplay/android-developer/answer/13327111)

출시 체크리스트:

- 개발자 계정·번들 id·서명 키·스토어 소유권·지원 이메일/URL 확보.
- 개인정보 처리방침을 실제 수집/전송/삭제와 일치시킴. App Privacy·Data safety·SDK 목록 작성.
- 계정 삭제 및 연결 데이터/알림 토큰/외부 처리자 데이터 정리 경로 검증.
- 사용자별 데이터 접근 통제, 계정 바꿔 로그인, 백업 복원, 로그 내 민감정보 검사.
- 데이터 내보내기 파일의 형식·단위·시간대·이전 기록 표시 정의.
- 심사용 계정 또는 충분한 데모, 실제 작동하는 backend, 권한 설명과 기능 설명 준비.
- 크래시/ANR·저장 실패·동기화 충돌 관측, 문의 응답 담당자·복구 절차·롤백 담당자 지정.
- 접근성·저사양 기기·백그라운드/강제 종료·앱 업데이트·재설치 테스트.
- 유료 디지털 기능을 도입하면 양 스토어 결제·구독·복원 정책을 출시 시점에 다시 검토.
- 출시 국가·연령·건강/금융 기능의 실제 범위가 정해지면 관련 신고/동의/정책을 추가 검토.

위는 기술·제품 준비 목록이며 법률 자문이나 포괄적 정책 준수 인증이 아니다. 정책·SDK 요구 버전은 제출 직전에 다시 확인한다.

## 16. 측정: 앱을 오래 보게 하는 것이 목표가 아니다

북극성 후보: **주간 계획을 이어간 사용자 수**.
정의는 해당 주에 유효한 루틴 계획이 있고, 최소 한 계획의 정규 기준 또는 사전 설정한 최소 기준을 주간 빈도만큼 충족한 고유 사용자 수.
정규 달성과 최소 기준 달성을 별도 분해한다. 비율도 함께 보며 낮은 기준 남발로 숫자만 높이지 않는지 조사한다.
실제 행동 증명은 자기보고 기록이므로 이 수치를 객관적인 삶의 개선으로 표현하지 않는다.

| 지표 | 정의 | 해석 주의 |
|---|---|---|
| 첫 설정 활성화 | first_open 후 24시간 내 첫 유효 루틴 생성 사용자 / 신규 사용자 | 기본 예시 자동 생성은 제외 |
| 첫 실천 활성화 | 첫 루틴 생성 후 7일 내 실제 값 > 0의 첫 기록 | ‘버튼 눌러 가입’과 구분; 최소/정규 분해 |
| D7 / D28 행동 유지 | 첫 루틴 생성일 기준 정확히 7일/28일째 유의미 기록 사용자 비율 | 분모는 관찰기간을 채운 cohort, 단순 앱 열기는 제외 |
| 주차 유지 | 생성 후 8–14일 / 22–28일에 유의미 기록이 있는 비율 | 주 1회 사용자 때문에 point-day 유지와 함께 봄 |
| 복귀율 | 예정 기회 두 번 연속 미기록 후 7일 내 새 실천한 사람 / 7일 추적 가능한 대상 | 주 N일은 미달한 주 기준으로 별도 cohort; 과거 소급 입력은 복귀 아님 |
| 계획 조정 유용성 | 변경을 적용한 뒤 다음 평가기간 기준을 충족한 비율 | 기존 충성 사용자 선택효과가 있어 인과효과로 단정 금지 |
| 기록 안전성 | 저장 실패·유실·중복·해결 안 된 충돌 건수 | ‘동기화 성공률’ 평균으로 유실 1건을 숨기지 않음 |
| 알림 부담 | 알림 off/권한 철회·반복 무반응·부담 인터뷰 | 권한 허용률을 단독 최적화하지 않음 |

유의미 기록은 실제 값이 양수인 실천/완료이며, 앱 열기·자동 추천·쉼 선택·소급 입력만으로 행동 유지의 분자를 늘리지 않는다.
루틴을 종료해 더 이상 앱이 필요 없는 성공 사례는 이탈 인터뷰에서 구분한다.

이벤트 제안: `habit_created`, `entry_recorded`, `entry_revised`, `habit_paused`, `habit_resumed`,
`review_completed`, `plan_adjustment_applied`, `reminder_opted_in`, `sync_failed`, `sync_conflict_resolved`.
안정적인 opId로 중복을 제거하고 source(app/widget/notification), schedule_type, entry_mode 등 허용 목록만 전송한다.
제목·이유·금액·자유 텍스트·실제 날짜별 상세 루틴은 분석 이벤트에 보내지 않는다.
identity 병합·분석 opt-out·시간대·늦게 도착한 오프라인 이벤트 처리 규칙도 계측 사양에 포함한다.
현재 이벤트를 실제 운영에서 수집·검증한 적이 있는지는 확인되지 않았다. 기존 문서의 baseline 계획을 측정 완료로 취급하지 않는다.

## 17. 검증 계획과 출시 게이트

### 설계 검증

1. 대상 사용자 6–8명: 최근 습관을 중단한 실제 상황과 사용 중인 도구를 듣는다. 구체 수치는 모집 제안이지 완료 실적이 아니다.
2. 프로토타입 테스트 5–8명: 금융 없이 시작, 루틴 생성, 작게 실천, 3일 후 복귀, 일정 변경, 기록 찾기.
3. 4주 비공개 베타 20–30명: 주기 유형별로 관찰하고 매주 짧은 인터뷰. 이 규모로 유의한 A/B 효과를 주장하지 않는다.
4. 계측의 분모·중복·누락부터 확인하고 이후 적절한 표본으로 효과 실험을 설계한다.

### 초기 품질 목표 — 업계 벤치마크가 아닌 내부 게이트 제안

- 신규 사용자의 80% 이상이 도움 없이 60초 내 첫 루틴 생성. 작은 표본의 경향 지표로만 사용.
- 완료/작게 실천/쉬기 의미를 테스트 참가자가 자신의 말로 구분할 수 있음.
- 홈 진입→기존 체크형 기록은 2탭 이내. 승인된 최소 기기에서 로컬 기록 피드백 p95 200ms 이하 목표.
- 네트워크 없이 앱을 다시 열어 예정 확인과 기록 가능. 계정 기능의 오프라인 제한은 별도 고지.
- 아래 신뢰성 테스트 전부 통과, 알려진 데이터 유실/교차 계정 노출/중복 집계 결함 0건.
- 핵심 흐름을 양 OS 화면 읽기 도구와 큰 글자로 완료. 실제 기기에서 검증.
- 계정 삭제/내보내기·지원/복구 경로·정책 제출 정보 준비.
- 4주 베타에서 데이터 유실 신고가 해결되지 않은 상태로 공개 출시하지 않음.
- 리텐션 목표치는 baseline 전에는 임의의 ‘D7 40%’를 약속하지 않음. baseline과 사용자 효용 면담으로 다음 게이트 결정.

### 출시를 막아야 하는 시나리오

| 시험 | 기대 결과 |
|---|---|
| 탭 직후 강제 종료 후 재실행 | 확인 표시된 기록은 남음, 실패했다면 거짓 성공 없음 |
| 비행기 모드 여러 기록 후 재연결 | 각 기록 한 번 반영, 저장 상태 전환 정확 |
| 두 기기에서 같은 기록 완료/취소 | 조용한 유실 없이 충돌 보존·선택 가능 |
| 루틴 요일 변경 | 마감된 과거 계획/완료율 불변 |
| 루틴 보관·복원 | 과거 기록 남음, 보관 기간은 예정 없음 |
| 주 3일 루틴을 같은 날 3회 누름 | 1일로 집계 |
| 목표 A 회고 후 목표 B 상세 | A의 결정이 B의 계획으로 표시되지 않음 |
| 자정·DST·시간대 변경 | 날짜 중복/소멸 없음, 과거 귀속 유지 |
| 알림 거부·기기 절전·정지 | 앱 기능 유지, 불필요한 재요청/예약 없음 |
| 게스트 + 기존 계정 | 양쪽 기록 보존 및 명시적 병합 |
| 계정 변경·삭제 후 오래된 기기 재접속 | 타인 기록 노출·삭제 데이터 부활 없음 |
| 구버전 금융 사용자 이전 두 번 실행 | 원본 보존·중복 없음·금융 계산 회귀 없음 |

## 18. 단계별 로드맵

가정: 개발자 2명 + 파트타임 제품/디자인·QA 지원. 일정은 확정 약속이 아니다.
기술 실험과 인력 확인 후 재산정한다. 일부 트랙을 겹치면 **약 12–16주**를 검토 범위로 잡되 스토어 심사 기간은 보장하지 않는다.
1인 개발이면 범위를 더 줄이거나 기간을 늘려야 한다.

| 단계 | 대략 기간 | 산출물 | 종료 조건 |
|---|---|---|---|
| 0. 방향·위험 검증 | 1–2주 | 인터뷰, 핵심 흐름 시안, 데이터 규칙, 양 OS 기술 실험/ADR | 목표 없이 시작·복귀 흐름 이해, 저장/알림 기술 경로 확인 |
| 1. 기록 기반 | 2–3주 | 계획 버전, 기록, pause/archive, outbox, 이전 어댑터 | 기록 불변·오프라인·충돌·이전 회귀 테스트 통과 |
| 2. 일상의 한 사이클 | 2–3주 | 게스트 온보딩, 오늘, 체크/수량/시간, 주 N일, 작게 실천, 로컬 알림 | 금융 없는 첫 실행→다음 날 반복 가능 |
| 3. 방향과 복귀 연결 | 2주 | 목표, 기록, 주간 돌아보기, 조정 적용, 재개 | 회고 변경이 예정과 알림에 실제 반영 |
| 4. 출시 준비 + 비공개 베타 | 최소 4주, 일부 병행 | 계정 권리, 데이터·접근성·기기 QA, 관측/지원, 스토어 패키지 | 출시 게이트 충족, 미해결 유실/보안 결함 없음 |
| 5. 검증 후 확장 | 출시 후 | 위젯·타이머·중간 목표·선택형 금융 도구 개선 | 실제 사용 데이터로 우선순위 재결정 |

첫 네이티브 검증은 단계 0, 보안·삭제 설계는 단계 1부터 시작한다. 마지막 주에 앱 껍데기와 정책을 붙이는 계획이 아니다.
두 OS 공통 도메인을 검증하되 테스트 참가자/실기기/개발자 계정 준비가 빠른 OS부터 베타할 수 있다. iOS 우선으로 임의 확정하지 않는다.

자동 머지는 CI·테스트·리뷰를 통과한 코드 변경에 사용한다. **스토어 제출·운영 데이터 마이그레이션·공개 출시까지 자동 승인된 것으로 확대 해석하지 않는다.**

## 20. 사업·성장 방향

첫 유입 메시지는 ‘목표 관리 플랫폼’보다 구체적 일상 장면으로 검증한다.
예: ‘퇴근 후 10분 읽기를 이어가고 싶을 때’, ‘주 3일 걷기를 일정에 맞추고 싶을 때’.
처음부터 많은 사용자를 사오는 광고보다 첫 4주 베타의 반복 효용을 먼저 확인한다.

기본 기록·되돌리기·쉬기·복귀·내보내기·삭제는 결제 장벽 밖에 둔다.
유료 후보는 축적된 기록의 깊은 회고, 고급 개인화, 선택형 도구처럼 지속 가치가 있는 기능이다.
가격·구독/일회성은 미확정이며 결제 의향과 운영 비용을 검증한 뒤 선택한다.
스트릭 복구·죄책감·사용자의 중단을 수익화하지 않는다.
공유가 필요하면 사용자가 고른 성취 한 장부터 시작하며 목표·금융 정보는 기본 비공개다.

## 21. 결정 요약과 다음 설계 단계

**확정:** 개인 중심, iOS/Android, 순차 출시 가능, 오늘/목표/기록 3탭, 금융의 선택형 전환, 지금은 화면 설계 우선.

**추천:** 독립 루틴 허용, 복귀·계획 조정 중심,
Expo/React Native 우선 기술 검증, 위젯은 v1.1이되 초기 PoC.

**아직 결정할 것:** 인력·기한·출시 국가, 첫 베타 OS, 금융 앱 내 제공 범위,
스토어 계정/운영 책임자, 스택 실험 결과, 수익모델, 시각 시안.

다음 산출물은 기능 추가가 아니라 **첫 루틴 만들기 / 오늘 실천 / 쉬었다가 복귀 / 주간 계획 조정**
네 흐름의 화면 시안과 상태 명세다. 현재 산출물은 `CORE_FLOWS_SCREEN_DESIGN.md`이며,
정적 검토용 시안과 정확한 화면별 명세를 먼저 제공한다. 클릭 가능한 프로토타입과 사용자 테스트는 다음 단계다.
그 결과를 검증한 뒤 LP-02~04를 시작한다.
시각 콘셉트와 구현 방식은 별도 확인 없이 승인된 것으로 기록하지 않는다.
